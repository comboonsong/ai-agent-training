# แผนแบ่งงานทีมแดชบอร์ดคุณภาพน้ำแม่น้ำกก

ทีมพัฒนา 3 คนแบ่งเป็น UX/UI 1 คน, Dev 1 รับผิดชอบ Frontend และ Dev 2 รับผิดชอบ Data/Backend โดยทำงานจาก [URD](../product/urd.md) ร่วมกัน เริ่มจากการเลือกจุดบนแผนที่และดูผลตรวจล่าสุดให้ทำงานครบตั้งแต่หน้าจอถึงข้อมูลจริง แล้วต่อยอดผลย้อนหลัง 7 วัน แนวโน้ม และคำแนะนำประชาชน

เอกสารนี้กำหนดผู้รับผิดชอบ สิ่งส่งมอบ การส่งต่องาน และการใช้สกิลที่ติดตั้งแล้ว ยังไม่ได้กำหนดรายชื่อบุคคลหรือวันส่งมอบ ให้ประเมินเวลาหลังตรวจข้อมูลจริงและสรุป PRD

## ผู้รับผิดชอบและสิ่งส่งมอบ

| บทบาท | งานรับผิดชอบหลัก | สิ่งส่งมอบ |
|---|---|---|
| UX/UI | ออกแบบลำดับการใช้งาน การเลือกจุดตรวจ แผนที่ ผลตรวจ กราฟย้อนหลัง และส่วนคำแนะนำ รวมถึงสถานะไม่มีข้อมูลและผลตรวจคนละวัน ทดสอบความเข้าใจของผู้ใช้ | แบบหน้าจอและต้นแบบ ข้อความบนหน้าจอ ข้อกำหนดการแสดงสถานะ และข้อค้นพบจากการทดสอบ |
| Dev 1 Frontend | พัฒนาหน้าจอ แผนที่ลำน้ำ กราฟ ตัวกรอง การแสดงเวลา และคำแนะนำ เชื่อม API และจัดการสถานะโหลดข้อมูล ไม่พบข้อมูล และข้อผิดพลาด | เว็บที่เริ่มทดสอบได้ด้วยข้อมูลตัวอย่างและเชื่อมข้อมูลจริงได้ การตรวจสอบพฤติกรรมหน้าจอ และผลตรวจงานร่วมกับ UX/UI |
| Dev 2 Data/Backend | ตรวจฐานข้อมูล GCP ทั้งสองตาราง หน่วยวัด รหัสจุดตรวจ วันเก็บตัวอย่าง และข้อมูลย้อนหลัง จับคู่เกณฑ์มาตรฐาน เตรียมข้อมูลจาก shapefile และพัฒนา API | รายละเอียดฟิลด์และหน่วย รูปแบบข้อมูลร่วม API ข้อมูลแผนที่พร้อมใช้ ตารางจับคู่มาตรฐาน และผลทดสอบการประมวลผลข้อมูล |

Dev ทั้งสองร่วมออกแบบระบบ ตรวจงานข้ามกัน เชื่อมระบบ และเตรียมการนำระบบขึ้นใช้งาน โดยแบ่งงานการนำขึ้นใช้งานให้ชัดใน system design และ phase plan

ผู้ตัดสินใจโครงการเป็นผู้กำหนดลำดับความสำคัญและปิดประเด็นความต้องการ บทบาทนี้อาจเป็นผู้ใช้หรือคนใดคนหนึ่งในทีม ไม่ได้สมมติว่ามีแรงงานเพิ่มอีกคน

คพ. เป็นผู้ให้บริการข้อมูลตาม URD ต้องตกลงผู้ตรวจรับเนื้อหาคำแนะนำแยกต่างหาก UX/UI รับผิดชอบการสื่อสารเนื้อหาที่ได้รับ ส่วนความถูกต้องของคำแนะนำต้องมีผู้รับผิดชอบที่โครงการระบุ

## ลำดับการทำงานและจุดส่งมอบร่วม

| ช่วงงาน | UX/UI | Dev 1 Frontend | Dev 2 Data/Backend | จุดส่งมอบร่วม |
|---|---|---|---|---|
| กำหนดรุ่นแรก | ร่วมจัดลำดับความต้องการและเส้นทางใช้งาน | ประเมินความเป็นไปได้ของหน้าจอ | ตรวจข้อมูลจริง หน่วย ความถี่การตรวจ และข้อจำกัด | PRD ตั้งต้นและเจ้าของประเด็นที่ยังเปิด |
| ออกแบบพร้อมกัน | ออกแบบ mockup จาก PRD | ช่วยตรวจแบบและออกแบบส่วน Frontend | นำการออกแบบระบบและ API | แบบหน้าจอ รูปแบบข้อมูลตัวอย่าง และ system design ที่สอดคล้องกัน |
| ผลล่าสุดบนแผนที่ | ตรวจการเลือกจุด การอ่านค่า วันตรวจ และสถานะ | ทำแผนที่กับรายละเอียดจุดจากข้อมูลตัวอย่าง แล้วเชื่อม API | เตรียมข้อมูลลำน้ำ ผลล่าสุด และเกณฑ์ที่จับคู่แล้ว | เลือกจุดบนแผนที่แล้วอ่านผลจริงและสถานะเทียบมาตรฐานได้ |
| ผลย้อนหลังและแนวโน้ม | ออกแบบช่วงเวลาและการแยกประเภทตัวอย่าง | ทำกราฟและการเลือกช่วงย้อนหลัง 7 วัน | ทำการค้นข้อมูลย้อนหลังและตรวจขอบเขตเวลา | ดูแนวโน้มของจุดเดียวกันและแยกวันตรวจของผิวน้ำกับตะกอนดินได้ |
| คำอธิบายและคำแนะนำ | จัดข้อความและทดสอบความเข้าใจ | แสดงคำอธิบายค่าและคำแนะนำตามกรณี | เชื่อมผลเกินเกณฑ์กับเนื้อหาที่กำหนด | แสดงคำแนะนำที่ผ่านการตรวจรับสำหรับกรณีที่เกี่ยวข้อง |
| ตรวจรับและส่งมอบ | ตรวจการใช้งานตามสถานการณ์ใน URD | ทดสอบหน้าจอและการเชื่อมระบบ | ตรวจผลกับข้อมูลต้นทางและทดสอบ API | ผลตรวจรับตาม URD และรายการประเด็นที่ยังต้องแก้ |

ช่วงงานในตารางเป็นลำดับตั้งต้นสำหรับนำไปจัด roadmap รายละเอียดและขนาดแต่ละช่วงจะสรุปหลังมี PRD และ system design งานเตรียมเนื้อหาคำแนะนำเริ่มได้ตั้งแต่ช่วงแรก แม้การแสดงผลจะเชื่อมในช่วงหลัง

## ข้อตกลงก่อนแยกทำ Frontend และ Backend

Dev ทั้งสองต้องตกลงรูปแบบข้อมูลและมีชุดข้อมูลตัวอย่างร่วมกัน เพื่อให้ Dev 1 ทำหน้าจอได้ระหว่างที่ Dev 2 เตรียมข้อมูลจริง โดยครอบคลุม:

- รหัสจุดตรวจ ชื่อจุดตรวจ และพิกัด
- ประเภทตัวอย่าง ได้แก่ ผิวน้ำและตะกอนดิน
- วันเวลาตรวจและหลักการเลือกผลล่าสุดของแต่ละประเภท
- ชื่อสารหรือค่าตรวจวัด ค่า และหน่วย
- เกณฑ์มาตรฐาน หน่วยของเกณฑ์ ผลการเปรียบเทียบ และปริมาณที่เกิน
- ผลย้อนหลังและนิยามช่วง 7 วัน
- รูปแบบข้อมูลลำน้ำที่จะส่งให้หน้าจอ
- รูปแบบคำอธิบายและคำแนะนำที่หน้าจอจะได้รับ

ข้อมูลตัวอย่างควรมีกรณีค่าปกติ เกินเกณฑ์ ไม่มีผลตรวจในช่วงที่เลือก ยังไม่มีเกณฑ์ที่จับคู่ และผลผิวน้ำกับตะกอนดินตรวจคนละวัน

ข้อกำหนดดูย้อนหลัง 7 วันไม่ได้หมายความว่ามีการตรวจทุกวัน ต้องตรวจความถี่จริงและออกแบบการแสดงช่วงที่ไม่มีผลตรวจร่วมกัน

ใช้ที่เก็บโค้ดเดียวกันโดยแยก branch ตามงาน มอบหมายผู้รับผิดชอบไฟล์หรือส่วนที่เปลี่ยนให้ชัด และตรวจการเปลี่ยนรูปแบบข้อมูลร่วมกันก่อนรวมโค้ด แต่ละรอบต้องมีจุดสาธิตการทำงานกับข้อมูลจริงร่วมกัน

## สกิลที่ใช้ในแผนนี้

รายชื่อต่อไปนี้ตรวจพบว่าติดตั้งบนเครื่องที่ใช้จัดทำโครงการแล้ว การใช้จากเครื่องของสมาชิกคนอื่นต้องตรวจการติดตั้งและสิทธิ์ของเครื่องนั้นด้วย

| สกิล | ผู้ใช้หลัก | ใช้เมื่อใดและได้อะไร |
|---|---|---|
| $prince-product:prd | ผู้ตัดสินใจโครงการและทั้งทีม | ใช้ URD แปลงความต้องการเป็นฟีเจอร์และลำดับความสำคัญ ได้ docs/product/prd.md |
| $prince-delivery:prototype-design | UX/UI ร่วมกับ Dev 1 | ออกแบบต้นแบบ เลือกโหมด mockup สำหรับทดสอบหน้าจอ ได้แบบใน docs/prototypes/<slug>/design.md |
| $prince-delivery:prototype-plan | UX/UI ร่วมกับ Dev 1 | ใช้เมื่อมีแบบต้นแบบและต้องการสร้างต้นแบบที่ทดลองใช้งานได้ ได้แผนใน docs/prototypes/<slug>/plan.md โค้ดต้นแบบต้องประเมินใหม่ก่อนนำไปใช้จริง |
| $prince-product:system-design | Dev 2 ร่วมกับ Dev 1 | ใช้หลังมี PRD เพื่อกำหนดองค์ประกอบระบบ ข้อมูล และการเชื่อมต่อ ได้ docs/architecture/system-design.md และบันทึกการตัดสินใจ |
| $prince-delivery:roadmap | ทั้งทีม | ใช้หลังมี PRD และ system design เลือกแบ่งงานขนานตามส่วนประกอบพร้อมจุดรวมระบบ ได้ docs/phases/phases.md |
| $prince-delivery:phase-design | Dev เจ้าของช่วงงาน | ออกแบบรายละเอียดของช่วงใน roadmap ได้ docs/phases/phase-NN/design.md |
| $prince-delivery:phase-plan | Dev เจ้าของช่วงงาน | ใช้หลังมี phase design เพื่อแตกงานลงมือทำ โดยอ้างอิงไฟล์จริง ได้ docs/phases/phase-NN/plan.md |
| $prince-core:simplify-review | Dev ที่ตรวจงาน | ใช้ตรวจความซับซ้อนเกินจำเป็นของโค้ด ต้องตรวจความถูกต้อง ความปลอดภัย และประสิทธิภาพด้วยวิธีอื่นเพิ่มเติมตามงาน |

prototype-design และ system-design ทำคู่ขนานได้หลังมี PRD ตั้งต้น จากนั้นใช้ roadmap กำหนดช่วงงาน ส่วน phase-design และ phase-plan ใช้กับช่วงที่กำลังจะลงมือทำ

ชุดที่ตรวจพบยังไม่มีสกิล execute ติดตั้งอยู่ หลังได้แผนสามารถสั่ง Codex ให้ทำงานตามแผนด้วยข้อความปกติ โดยระบุงานและขอบเขตไฟล์ที่แต่ละคนรับผิดชอบ

## ตัวอย่างข้อความเรียกใช้สกิล

เปิดโครงการนี้ใน Codex แล้วพิมพ์ชื่อสกิลพร้อมโจทย์ในช่องแชต Codex รองรับการเรียกสกิลด้วยเครื่องหมาย $ ตาม [เอกสาร OpenAI](https://developers.openai.com/plugins/build/skills)

### เริ่มสร้าง PRD ร่วมกัน

~~~text
$prince-product:prd
ใช้ docs/product/urd.md ของโครงการแดชบอร์ดคุณภาพน้ำแม่น้ำกก
ทีมมี UX/UI 1 คน และ Dev 2 คน
ช่วยกำหนดฟีเจอร์และลำดับความสำคัญของรุ่นแรก
เก็บเรื่องที่ยังไม่มีคำตอบเป็นประเด็นเปิด
ถามทีละข้อและใช้ตัวเลือกไม่เกิน 10 ข้อ
~~~

### ออกแบบต้นแบบหน้าจอ

~~~text
$prince-delivery:prototype-design
ออกแบบ mockup สำหรับประชาชนทั่วไปจาก PRD
เน้นการเลือกจุดตรวจ อ่านผลและวันตรวจ ดูแนวโน้มย้อนหลัง 7 วัน
และเข้าใจคำแนะนำเมื่อสารพิษเกินมาตรฐาน
ระบุข้อความคำแนะนำที่ยังรอเนื้อหาจริงไว้ให้ชัดเจน
~~~

หากต้องสร้างต้นแบบที่ทดลองใช้งานได้ ให้เรียก $prince-delivery:prototype-plan พร้อมระบุไฟล์ design.md ของต้นแบบที่เพิ่งจัดทำ

### ออกแบบระบบ

~~~text
$prince-product:system-design
ออกแบบระบบจาก PRD สำหรับ Dev 2 คน
ครอบคลุมฐานข้อมูล GCP สองตาราง ข้อมูลลำน้ำจาก shapefile
API และเว็บแดชบอร์ด
กำหนดรูปแบบข้อมูลร่วมกันให้ Frontend และ Backend ทำงานขนานได้
ตรวจสอบบริการฐานข้อมูลและข้อจำกัดจริงก่อนสรุปเทคโนโลยี
~~~

### จัดลำดับและแบ่งงานขนาน

~~~text
$prince-delivery:roadmap
ใช้ PRD และ system design ของโครงการ
วางแผนสำหรับ UX/UI 1 คน Frontend 1 คน และ Data/Backend 1 คน
ต้องการแบ่งงานขนานตามส่วนประกอบ
ระบุเจ้าของงาน สิ่งที่ต้องรอกัน และจุดรวมระบบในแต่ละรอบ
~~~

### ออกแบบและแตกงานของช่วงแรก

ใช้ทีละข้อความตามลำดับ หลัง roadmap ระบุ phase-01 แล้ว:


เมื่อต้องลงมือพัฒนา ใช้ข้อความปกติ เช่น:

~~~text

ใช้รูปแบบข้อมูลที่ตกลงร่วมกัน และตรวจผลตามแผน
~~~

## งานเริ่มต้นของแต่ละคน

1. ทั้งทีมใช้สกิล prd จาก URD ฉบับล่าสุดเพื่อสรุปฟีเจอร์รุ่นแรก
2. UX/UI ร่างเส้นทางเลือกจุดและอ่านผลล่าสุด พร้อมรายการข้อมูลที่ต้องเห็นบนหน้าจอ
3. Dev 2 ตรวจแหล่งข้อมูลจริงและจัดทำตัวอย่างข้อมูลของจุดตรวจหนึ่งจุดสำหรับทั้งสองประเภท
4. Dev 1 และ Dev 2 ตกลงรูปแบบข้อมูลร่วมกัน แล้ว Dev 1 เริ่มหน้าจอด้วยข้อมูลตัวอย่าง
5. ทั้งทีมกำหนดจุดรวมระบบรอบแรก โดยตรวจผลบนหน้าจอเทียบกับข้อมูลต้นทางและเกณฑ์ใน URD
