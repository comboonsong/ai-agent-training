# Phase 01 — งานประมวลผลข้อมูลตามรอบและชุดข้อมูลให้บริการ

## Phase & scope

ช่วงงาน Back-end ของ Wave 1 ตาม roadmap: อ่านตารางผิวน้ำและตะกอนดินจาก BigQuery แปลงเป็นผลตรวจรูปแบบเดียวกัน เลือกผลล่าสุดของแต่ละจุด ค่าตรวจวัด และประเภทตัวอย่าง แล้วเผยแพร่จุดตรวจกับผลล่าสุดเป็นชุดข้อมูลให้บริการตามรูปแบบที่ตกลงกับ Front-end เมื่ออ่านต้นทางไม่ได้ ชุดเดิมต้องอยู่ครบ

- **Serves:** ผลตรวจล่าสุดรายจุด, แผนที่จุดตรวจและทิศทางการไหล
- **Touches:** งานประมวลผลข้อมูลตามรอบ, ชุดข้อมูลให้บริการ
- **Depends on:** none
- **Estimate:** 6–8 tasks

ส่งต่อให้ช่วงอื่น: ผลครั้งก่อนหน้าและเปอร์เซ็นต์ การเทียบมาตรฐาน และผลย้อนหลัง 7 วัน (Phase 05) แนวลำน้ำ (Phase 09) การแจ้งเตือน (Phase 13) การตั้งเวลารันอัตโนมัติ และการนำขึ้นที่วางระบบจริง (ADR 002) ช่วงนี้รันด้วยคำสั่งบนเครื่องของทีม

ผู้ใช้ยืนยันขอบเขตนี้แล้ว รวมถึงการส่งผลครั้งก่อนหน้าไปทำใน Phase 05 การทวนหัวข้ออื่นของเอกสารนี้หยุดตามที่ผู้ใช้ขอ หัวข้อตั้งแต่ *What already exists* ลงไปเป็นร่างที่ยังไม่ได้ทวน

## What already exists

- ค้นทั้ง repo แล้ว ไม่พบโค้ดหรือไฟล์ dependency ใด นอกจากเอกสารและ `note.txt` ทุกส่วนในช่วงนี้จึงเป็นของใหม่ ยังไม่ได้ยืนยันกับผู้ใช้ว่ามีโค้ดอ่านข้อมูลชุดนี้อยู่นอก repo หรือไม่
- system design ยังไม่มีหัวข้อ *Fitness functions* และยังไม่มี threat model จึงไม่มีการตรวจเดิมที่ช่วงนี้ต้องผ่าน
- ต้นทาง อ่านโครงสร้างด้วย `bq show` แล้ว ไม่ได้อ่านแถวข้อมูล: view `envilink-data-platform.standardized__kok_river.pcd_water_quality` และ `envilink-data-platform.standardized__kok_river.pcd_sediment_quality` ใน `asia-southeast1`
  - ข้อมูลแบบกว้าง: หนึ่งแถวคือการเก็บตัวอย่างหนึ่งครั้ง ณ จุดหนึ่ง ค่าตรวจวัดแต่ละตัวมีคอลัมน์ `<ค่า>_<หน่วย>_value` (FLOAT) คู่กับ `<ค่า>_<หน่วย>_qualifier` (STRING)
  - ผิวน้ำมี 27 ค่าตรวจวัด ตะกอนดินมี 12 ค่า
  - ฟิลด์ร่วม: `station_code`, `province`, `river_name`, `location_name`, `latitude`, `longitude`, `region`, `round`, `sample_date` (DATE), `sample_time` (STRING), `remark`, `data_date` (DATE), `load_timestamp` (TIMESTAMP)
  - ผิวน้ำมีเพิ่ม: `water_source_type`, `sampler_name`, `watershed`
- ภาษา Python 3.11 (มีบนเครื่องแล้ว) ตามที่ผู้ใช้ยืนยันในช่วงนี้ เพิ่ม dependency ใหม่หนึ่งตัวคือไลบรารี BigQuery ของ Google การแปลงข้อมูลและการเขียนไฟล์ใช้ standard library ทั้งหมด
- ฐานข้อมูลต้นทางเป็น BigQuery ตามที่ผู้ใช้ยืนยันในช่วงนี้

## Components & interfaces

- **ทะเบียนค่าตรวจวัด** — รายการคอลัมน์ที่รู้จักของแต่ละตาราง เขียนไว้ตรง ๆ ไม่เดาจากรูปแบบชื่อ แต่ละรายการบอกรหัสค่าตรวจวัด ประเภทตัวอย่าง ชื่อคอลัมน์ value และ qualifier และหน่วย ตะกั่วในผิวน้ำ (mg/L) กับในตะกอนดิน (mg/kg) เป็นคนละรายการแม้ใช้รหัสค่าตรวจวัดเดียวกัน ไม่พึ่งส่วนอื่น
- **ตัวอ่านต้นทาง** — query view ทั้งสองแบบอ่านอย่างเดียว เลือกเฉพาะคอลัมน์ในทะเบียนและฟิลด์จุดตรวจ ไม่เลือก `sampler_name` และ `remark` เปิดให้ส่วนอื่นใช้ผ่าน interface เดียว คือคืนแถวของแต่ละตารางเป็น mapping ชื่อคอลัมน์ต่อค่า การทดสอบจึงใช้แถวตัวอย่างแทน BigQuery ได้ พึ่งทะเบียนค่าตรวจวัด
- **ตัวแปลงรูปแบบ** — แปลงแถวแบบกว้างเป็นผลตรวจทีละค่า ได้แก่ จุดตรวจ ประเภทตัวอย่าง ค่าตรวจวัด ค่า qualifier หน่วย และวันเวลาที่ตรวจ ค่าตรวจวัดที่ทั้ง value และ qualifier ว่างไม่สร้างผลตรวจ พึ่งทะเบียนค่าตรวจวัด
- **ตัวรวมจุดตรวจ** — สร้างรายการจุดตรวจจากแถวของทั้งสองตาราง ได้แก่ รหัส ชื่อ ลำน้ำ จังหวัด และพิกัด ไม่พึ่งส่วนอื่น
- **ตัวเลือกผลล่าสุด** — สำหรับแต่ละ (จุดตรวจ, ประเภทตัวอย่าง, ค่าตรวจวัด) เลือกผลที่วันเวลาตรวจล่าสุด พึ่งผลตรวจจากตัวแปลงรูปแบบ
- **ตัวเผยแพร่** — เขียนชุดข้อมูลให้บริการลงโฟลเดอร์ปลายทางครั้งละทั้งชุด: เขียนลงโฟลเดอร์ชั่วคราวให้ครบก่อน แล้วสลับเข้าแทนชุดเดิม และลบชุดเดิมหลังสลับสำเร็จ ชุดหนึ่งมีไฟล์จุดตรวจ ไฟล์ผลล่าสุด และไฟล์ข้อมูลรอบ ไฟล์ข้อมูลรอบบอกเลขรุ่นของรูปแบบไฟล์ เวลาประมวลผล จำนวนแถวที่อ่าน จำนวนแถวที่ข้าม และคอลัมน์ที่ไม่รู้จัก เมื่อรูปแบบไฟล์เปลี่ยนแบบที่เว็บรุ่นเก่าอ่านไม่ได้ เลขรุ่นต้องขึ้น พึ่งรายการจุดตรวจและผลล่าสุด
- **คำสั่งรัน** — รันทั้งรอบด้วยคำสั่งเดียว รับโฟลเดอร์ปลายทาง และโปรเจกต์กับ dataset ต้นทาง ซึ่งมีค่าเริ่มต้นเป็นตำแหน่งด้านบน สิทธิ์อ่าน BigQuery มาจาก Application Default Credentials ของเครื่อง ไม่มีรหัสผ่านหรือคีย์ในโค้ดหรือใน repo พิมพ์สรุปรอบ และคืน exit code ไม่เป็นศูนย์เมื่อรอบล้มเหลว พึ่งทุกส่วนด้านบน

> **Open:** รูปแบบไฟล์ของชุดข้อมูลให้บริการ (ชื่อไฟล์ ฟิลด์ การแบ่งไฟล์) ต้องตกลงกับ Dev 1 ก่อน Phase 02 ใช้ข้อมูลตัวอย่าง

## Data flow

1. คำสั่งรันเริ่มรอบ
2. ตัวอ่านต้นทาง query view ทั้งสองแบบ synchronous อ่านอย่างเดียว การรันซ้ำไม่เปลี่ยนอะไรที่ต้นทาง ได้แถวแบบกว้าง
3. ตัวแปลงรูปแบบใช้ทะเบียน แปลงแต่ละแถวเป็นผลตรวจทีละค่า
4. ตัวรวมจุดตรวจสร้างรายการจุดตรวจ ตัวเลือกผลล่าสุดเลือกผลของแต่ละคีย์
5. ตัวเผยแพร่เขียนชุดใหม่ลงโฟลเดอร์ชั่วคราว แล้วสลับเข้าแทนชุดเดิม
6. คำสั่งรันพิมพ์สรุปรอบ และจบด้วย exit code 0

## Error handling

- **อ่าน BigQuery ไม่ได้** (สิทธิ์หมดอายุ เครือข่าย view หาย query เกินเวลา) — ไม่ลองใหม่อัตโนมัติ รอบล้มเหลวก่อนเขียนอะไร ชุดเดิมไม่ถูกแตะ พิมพ์สาเหตุ และ exit code ไม่เป็นศูนย์ ผู้รันสั่งรอบใหม่เอง
- **คอลัมน์ในทะเบียนหายจาก view** — รอบล้มเหลว เพราะจะเผยแพร่ข้อมูลไม่ครบโดยไม่มีใครรู้
- **view มีคอลัมน์ค่าตรวจวัดใหม่ที่ไม่อยู่ในทะเบียน** — ข้าม และบันทึกชื่อคอลัมน์ในสรุปรอบและไฟล์ข้อมูลรอบ
- **แถวไม่มี `station_code` พิกัด หรือ `sample_date`** — ข้ามแถวนั้น และนับในสรุปรอบ
- **แถวซ้ำที่คีย์เดียวกัน** — เลือกแถวที่ `load_timestamp` ล่าสุด
- **เขียนชุดใหม่ไม่สำเร็จระหว่างทาง** — ชุดเดิมยังอยู่ครบ โฟลเดอร์ชั่วคราวถูกลบ

## Proving it works

1. แต่ละจุดตรวจได้ผลล่าสุดแยกผิวน้ำกับตะกอนดิน พร้อมวันเวลาที่ตรวจของแต่ละประเภท แม้ตรวจคนละวัน
2. ผลล่าสุดที่เผยแพร่ตรงกับแถวต้นทาง ทั้งค่า qualifier และหน่วย
3. หน่วยมาจากทะเบียน ตะกั่วผิวน้ำเป็น mg/L ตะกอนดินเป็น mg/kg
4. จุดที่มีผลประเภทเดียวแสดงเฉพาะประเภทนั้น ไม่มีค่าว่างของอีกประเภทปลอมขึ้นมา
5. ค่าที่มี qualifier แต่ไม่มีตัวเลข ถูกเผยแพร่โดยเก็บ qualifier ไว้ ไม่ถูกแปลงเป็นศูนย์
6. ชุดที่เผยแพร่ไม่มี `sampler_name` และ `remark` และ query ที่ส่งไป BigQuery ไม่เลือกสองคอลัมน์นี้
7. เมื่ออ่านต้นทางไม่ได้ หรือคอลัมน์ในทะเบียนหาย ชุดเดิมไม่เปลี่ยนแม้แต่ไบต์เดียว และ exit code ไม่เป็นศูนย์
8. รันซ้ำกับข้อมูลเดิมได้ชุดเดิมทุกไฟล์ ยกเว้นเวลาประมวลผล
9. แถวที่ข้ามและคอลัมน์ที่ไม่รู้จักถูกนับในสรุปรอบ
10. ไฟล์ข้อมูลรอบบอกเลขรุ่นของรูปแบบไฟล์

การทดสอบใช้แถวตัวอย่างแทน BigQuery และมีการรันจริงกับ view หนึ่งครั้งเป็นการตรวจด้วยมือ

## Rejected alternatives

- **แปลงข้อมูลกว้างเป็นยาวใน BigQuery ด้วย UNPIVOT** — ทดสอบได้เฉพาะเมื่อต่อ BigQuery ได้ และทะเบียนจะไปอยู่ใน SQL แพ้เพราะการแปลงใน Python ทดสอบด้วยแถวตัวอย่างบนเครื่องได้
- **อ่านทุกคอลัมน์แล้วกรองทีหลัง** — `sampler_name` จะเข้ามาในหน่วยความจำและเสี่ยงหลุดลงไฟล์ แพ้เพราะการเลือกคอลัมน์ตั้งแต่ query ทำให้ข้อมูลบุคคลไม่เข้าระบบเลย
- **หาค่าตรวจวัดและหน่วยจากรูปแบบชื่อคอลัมน์อัตโนมัติ** — ชื่ออย่าง `total_coliform_mpn_100ml` แยกค่ากับหน่วยได้ไม่แน่นอน และคอลัมน์ใหม่จะถูกเผยแพร่โดยไม่มีใครตรวจ
- **ลองอ่าน BigQuery ใหม่อัตโนมัติเมื่อล้มเหลว** — ช่วงนี้รันด้วยมือบนเครื่อง ผู้รันเห็นความล้มเหลวทันทีและสั่งใหม่ได้ การลองใหม่จะซ่อนสิทธิ์หมดอายุไว้หลังเวลารอ ทบทวนอีกครั้งเมื่อมีการตั้งเวลารันอัตโนมัติ

## Open questions

> **Open:** `sample_time` เป็น STRING ยังไม่รู้รูปแบบ และยังไม่รู้เขตเวลา (สันนิษฐานว่าเวลาไทย) ใช้เรียงหาผลล่าสุด

> **Open:** "ผลล่าสุด" ยึด `sample_date` + `sample_time` ไม่ใช่ `data_date` หรือ `load_timestamp`

> **Open:** ความหมายของ `round` และควรใช้ร่วมเรียงลำดับหรือไม่

> **Open:** ค่าที่อยู่ใน qualifier มีอะไรบ้าง เช่น `<` หรือ `ND`

> **Open:** WQI เป็นดัชนีที่คำนวณแล้ว ไม่ใช่ค่าที่วัด จะเผยแพร่เป็นค่าตรวจวัดตัวหนึ่งหรือไม่

> **Open:** เมื่อจุดเดียวกันมีพิกัดหรือชื่อไม่ตรงกันระหว่างสองตาราง จะใช้ค่าจากตารางใด

> **Open:** รูปแบบไฟล์ชุดข้อมูลให้บริการ ต้องตกลงกับ Dev 1

> **Open:** โฟลเดอร์ปลายทางบนเครื่อง และวิธีที่เว็บอ่านไฟล์ระหว่างพัฒนา (เชื่อมจริงใน Phase 04)

> **Open:** มีโค้ดหรือสคริปต์อ่านข้อมูลชุดนี้อยู่นอก repo หรือไม่ ยังไม่ได้ยืนยันกับผู้ใช้

> **Open:** ภาษา Python และไลบรารี BigQuery ยืนยันแล้วในช่วงนี้ แต่ ADR 002 ยังเป็น proposed ต้องรัน system-design เพื่อบันทึกการตัดสินใจเรื่องภาษาเป็น ADR ที่ accepted (checklist: Maintainability)

> **Open:** ขนาดไฟล์ผลล่าสุดเทียบกับเป้าหมาย 5 วินาทีของหน้าเว็บ ยังไม่รู้จำนวนแถวจริงเพราะต้นทางเป็น view (checklist: Performance)

> **Open:** ยังไม่มี threat model ควรรัน `/prince-guardrails:threat-model` ก่อนนำระบบขึ้นให้ประชาชนใช้ ช่วงนี้ปิดความเสี่ยงด้านข้อมูลบุคคลด้วยการไม่เลือก `sampler_name` และ `remark` (checklist: Security & privacy)
